# 官方 OCR 对照与接入记录

## 0.3.0：直接运行原版 OCR 组件（当前实现）

用户反馈0.2.1仍无法识别，并明确要求直接复用官方成熟的处理方式。0.3.0已移除Tesseract.js、自制预处理、单词候选提取和二次放大复核。识别由未修改的 `room-code-assistant-worker.exe` 完成，随包原样包含其59个原始文件和独立SHA256清单。

原组件来自本机安装目录 `%LOCALAPPDATA%\com.administrator.fps-vantix\LivePlayerHost\runtime\ocr`，不随源码上传。worker SHA256为 `84b1f83c225331431f2fc19c7e6569f637d92076636bb1e3a16697b9a90598c5`。没有取得该原生worker的源代码，直接调用原二进制保留其内部识别逻辑。

根据官方 `ocr-frame-bridge.js` 与宿主IL对齐这些处理：

- 裁剪原始video/canvas：左上floor、右下ceil；宽度最多1280，仅缩小，不补边、不放大。
- 裁剪面积≤400000用PNG，更大用JPEG quality 0.9；默认Canvas平滑设置。
- 宿主解码并按 `[2,1,0,3]` 将BGRA换为RGBA，再提交原组件。
- 启动参数 `ipc`，工作目录为原OCR目录，沿用官方语言、白名单、DLL与tessdata环境变量。
- 请求为小端长度前缀JSON（含sequence、尺寸、pattern、required_frames:1、rgba_len）加RGBA；直接采用原版raw/candidate/confidence。
- 播放器保留最新帧元数据、单请求占位、延后取帧及ACK后立即继续处理；不累积过期图像，旧会话结果隔离。Electron宿主保留已有后台识别能力。
- 宿主确认要求置信度≥80、至少两次一致观察；播放器150ms、桌面100ms。每次会话仅确认一次。

独立原安装worker与包内副本已在14次固定输入上逐项比较，raw/candidate/confidence/type/error一致，记录在 `artifacts/official-ocr-parity.json`。另以GDI+对照Electron解码：PNG全部221像素、JPEG采样250像素的RGBA一致。此为组件与已测输入的一致性验证，不能等同于所有直播的识别成功率。

部分官方WebCodecs路径使用共享RGBA内存，本应用在对应面积使用无损PNG IPC；桌面采集沿用本应用的系统采集接口。播放器、桌面采集和输入宿主并非完整移植官方程序。开发版与打包EXE的7项选区对照均通过：6个清晰样本双帧确认，低清样本双方拒绝。用户本次缩放截图在原版worker中也未形成候选；尚需以直播原始帧现场复测。

## 官方如何处理

1. 从视频原始像素按归一化选区裁剪；宽度超过 1280 才缩小。Web 层不做锐化或二值化。
2. 独立原生 worker 调用 Tesseract。默认单行模式 PSM7，并有稀疏模式 PSM11。日志中可见行定位、小字和多尺度处理；实际码行识别高度包括 48、56、64，外围约 20px 留白。字符串与日志还表明它结合字符候选、置信度和边界筛选。没有恢复完整阈值、行提取或分支选择算法。
3. 使用英文模型和大小写字母/数字白名单。模型 SHA256 与公开 `tessdata_fast/4.1.0/eng.traineddata` 完全一致：`7d4322bd2a7749724879683fc3912cb542f19906c83bcc1a52132556427170b2`。
4. 宿主仍要求候选置信度至少 80、至少两帧一致；播放器跨至少 150ms，桌面跨至少 100ms。通过后写剪贴板并回读。

依据为本地宿主IL分析与隔离IPC探针；分析资料和日志仅本地保存。Web入口为安装组件的 `Web/ocr-frame-bridge.js`。原生worker SHA256：`84b1f83c225331431f2fc19c7e6569f637d92076636bb1e3a16697b9a90598c5`。REA只确认目标身份，未恢复完整原生源码。

## 自制版的实际问题与最小修复

之前使用不同的 `best_int` 英文模型。裁剪目标高度 96 以整个选区计算，选区高于 96 时可能完全不放大，弹窗中的 9～14px 字符仍然过小。首次 OCR 没形成合法候选时，后续码字复核也无法启动。

0.2.1 改用上述公开 fast 模型，校验下载哈希并随包离线使用；大小写白名单、空格设置与观察到的官方值一致。裁剪最小放大倍数改为 2，继续限制在 1280×720。现有同码局部复核、80 门槛、双帧确认和取消隔离继续使用。没有复制官方私有 worker，也没有声称实现其完整多行/字符证据算法。

## 真实回归

固定样本为本地私有游戏弹窗；原始截图、实际邀请码及样本清单不随仓库上传。缩小尺寸和生成方法保存在本地 `tests/fixtures/valorant-dialog-downscales.json`。

| 完整弹窗 | 修复前生产流程 | 0.2.1 生产流程 |
| --- | --- | --- |
| 原图 915×502 | 两帧确认，83 | 两帧确认，88 |
| 0.75 倍 686×377 | 原彩 76、增强 0，8帧未确认 | 两帧确认，92 |

`npm run test:regions` 运行真实 Electron、Canvas 裁剪、OCR、IPC 和剪贴板回读。还覆盖紧文字、整输入框、输入框加按钮；每轮确认后只发一个事件，并忽略后续帧。旧基线在 `artifacts/ocr-regions-baseline-probe/`，新结果在 `artifacts/ocr-regions-after-guard/`。曾并发运行的两个探针发生系统剪贴板互相覆盖，其结果不计入验证；正式验证串行执行。

另运行原有 50 轮基准：最初原版正确 43/50，本次 47/50，错误确认均为 0；清晰码确认中位耗时 234ms→226ms，宽选区 1/3→3/3。上一次 best 模型优化曾达到 48/50，本次 fast 在部分合成 `XYZ789` 小字/模糊样本上退化，因此这次修复针对真实游戏小弹窗，不能宣称所有字体上都更好。详细逐帧结果在 `artifacts/ocr-benchmark.json`。

资源准备、启动和打包都校验模型 SHA256。缺失或损坏模型会立即报错，不会进入 Tesseract.js 的永久初始化等待；两项异常回归已加入 `npm test`。

发布目录 `dist/FrameCode-win32-x64/` 和 ZIP `dist/FrameCode-0.2.1-win32-x64.zip` 已生成。`npm run test:packaged` 验证启动、离线 OCR、剪贴板和桌面窗口采集；同一组 6 个正样本和 1 个低清负样本也通过打包程序验证，结果在 `artifacts/ocr-regions-packaged/`。

## 低清截图的边界

用户本次截图左侧选区 430×187，文字只有约 6～7px 高。旧版把多行选区按单行读取，得到 `BE HE`、置信度 0。该缩放后的截图经官方 worker 19 次识别也未形成候选，这不等于官方读取原直播帧时失败。

实验中存在错误候选且置信度超过80的局部处理组合，故不能降低门槛或从大量裁剪结果中取最高分。0.2.1在固定截图上连续8帧仍拒绝确认，没有改写剪贴板；这作为低清负样本回归。该版本的固定图片测试不代表所有直播的识别成功率。0.3.0接入原版组件后，使用者已现场确认识别可用。
